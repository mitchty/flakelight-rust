* flakelight-rust

Highly opinionated nix flakelight module for rust development using [[https://github.com/nix-community/flakelight][flakelight]], built on top of [[https://github.com/ipetkov/crane][crane]] + [[https://github.com/nix-community/fenix][fenix]] behind the scenes for the rust toolchain shenanigans.

Unlike [[https://github.com/accelbread/flakelight-rust][accelbread/flakelight-rust]] which is naersk-based and constrained to nixpkgs rust and overall toolchain setup, this module enables more easy setup of things like:
- Pinned/tracked fenix toolchain for customizing the rust version in use
- Windows cross-compilation to ~x86_64-pc-windows-gnu~ via mingw64, note Linux only
- Ability to easily customize rust binary targets to be fully static for Linux, static...ish for macos
- Ability to easily setup tracing/profiling targets
- Easy ability to add wasm targets as well for crates so that native and wasm are treated as equals
- A default more "development" checks/devShell set for interactive builds ie:
  * clippy is setup to deny warnings for release profile builds
  * cargo doc also setup to deny warnings for any documentation
  * cargo-nextest to allow for easy unit test integration
  * cargo-deny to help detecting duplicate crates as well as license or dependency-graph drift
  * optional cargo-audit check via ~audit.enable~ against a rustsec advisory db input for CVE scanning
  * an ~update~ app to make day to day development updates easy
- Treefmt setup and check integration

This is a bit of a POC for now, I will be dogfooding it for myself on my own projects first as that is where most of this nonsense originates from anyway. Basically I wanted to make my nix rust development much simpler when I start new projects as well as keep them in sync betwixt them all as it was getting a bit obscene the drift between disparate rust projects and given I am a nix fan and flakelight abuser might as well try fixing the DRY/WET problem at its source.

** Options (WIP I threw in all the crap I abuse for now)

Note the exmaples dir is probably the best source of how you can use this.

*** ~fileset~

Configures the fileset the rust package/crate is built with. Defaults to all ~rust~, ~Cargo.toml~, and ~Cargo.lock~ files so simple use cases "just work". More complex setups can customize this.

*** ~crossSystems~

Exists to map a rustc target triple, ex: ~x86_64-pc-windows-gnu~ directly to a nixpkgs ~crossSystem~ attrset, used when a variant's ~target~ requires a different host platform, ex: Windows cross compiles.

Targets without an entry ex: ~wasm32-unknown-unknown~ still get the fenix ~rust-std~ target added to the toolchain derivation, just without a different nixpkgs.

*** ~cargoDenyPackage~

The ~cargo-deny~ package derivation used by the ~dotdeps~ app for dep-graph output, here cause cargo deny needs the ~-g~ flag for dotdeps. Defaults to this module's pinned ~packages.cargo-deny-0_19~ derivation so I know dep graph stuff works.

*** ~audit.enable~

Off by default. When true, adds a ~checks."${pname}-audit"~ derivation that runs ~cargo audit~ via crane against the ~advisory-db~ flake input.

The default input for it is ~github:rustsec/advisory-db~ but can changed by callers via ~inputs.advisory-db.follows~ or `lib.mkForce` on ~flakelightModule~'s ~inputs.advisory-db~.

*** ~binaries.NAME~

Manually declare a rust binary with options:

**** ~crate~, ~pathDeps~

The binaries crate dir plus any shared workspace crates it depends on.

Note this is to allow for multi binary and lib crate workspaces where a binary may depend upon a subset of library crates. This helps save needless recompilation for dependencies.

When used, the binary file set is computed to cover just the relevant crates via ~craneLib.fileset.commonCargoSources~ overlaid on top of a fake full-workspace source, so that cargo's workspace resolution still sees every workspace crate members.

This is here mostly for things like a gui binary, and cli binary where the cli might have much smaller dependency chains to the gui binary. This also helps reducing dep rebuilds in crane dep chains.

You may override this whole approach entirely by using the ~fileset~ attribute to give everything manually.

**** ~cargoExtraArgs~

Extra ~cargo~ args to build the with e.g. ~"-p my-crate"~ Defaults to ~"-p <name>"~.

**** ~nativeBuildInputs~, ~buildInputs~, ~env~, ~overrideCraneArgs~, ~extraCraneArgs~, ~postProcess~

Used to force override inputs if needed per variant/crate derivation.

~overrideCraneArgs~
Is mostly an emergency escape hatch for when you need to surgically replace or update attr sets. It receives ~{ commonArgs, ... }~ ~commonArgs~ being the derivation ~src~, ~pname~, ~cargoExtraArgs~, ~nativeBuildInputs~, ~buildInputs~, ~env~, etc... and its return is the crane ~commonArgs~ directly. For regular additive attr set merge use ~extraCraneArgs~ below.

~extraCraneArgs~
The more "normal" approach to attr set merging in nix/nixpkgs lib type stuff. All merges are done via ~//~ on top of the final ~commonArgs~, note it runs after ^^^ ~overrideCraneArgs~. Less of a pain to use in remembering to merge ~commonArgs~ yourself.

**** ~variants.NAME~

Suffix named build variant(s) of this binary. The ~default~ variant produces ~packages.NAME~ any other name produces  ~packages.NAME-VARIANT~. Each variant contains:
  - ~systems~
    Nix triples for this variant to build against. ~null~ which is default means all systems.
    Useful for things like CUDA builds which are only relevant for Linux. Maybe Windows but I don't use that for cuda.
  - ~target~
    Rustc target triple to build against, or ~null~ for native host platform target.
  - ~pkgs~
    Nix function of ~{ pkgs, lib, system, target }~ returning the ~pkgs~ attrset to build the variant against
    Ex to enable CUDA on a pkgs attrset ~{ pkgs, system, ... }: import pkgs.path { inherit system; config.cudaSupport = true; }~
  - ~cargoProfile~, ~rustflags~, ~extraCargoExtraArgs~
    Cargo profile name, set via ~CARGO_PROFILE~, ~RUSTFLAGS~, and args appended to ~cargoExtraArgs~ ex: ~--features foo/bar~.
  - ~env~, ~nativeBuildInputs~, ~buildInputs~
    Nix attrsets merged on top of the parent binaries attrsets like most nixpkgs approaches.
    Inputs are already resolved when ~env~ runs, so things like ~LD_LIBRARY_PATH = lib.makeLibraryPath buildInputs~ just work.
  - ~overrideCraneArgs~, ~extraCraneArgs~, ~postProcess~
    ~overrideCraneArgs~ overrides the parent binary's ~overrideCraneArgs~ entirely if set.
    ~extraCraneArgs~ is merged with ~//~ on top of the parent binaries ~extraCraneArgs~ result attr set. Done after override cause the other way around seems silly af.
  - ~portable~
    Only meaningful when ~target == null~ aka native builds. On Linux, builds a musl based static elf binary by cross compiling for ~<hostArch>-unknown-linux-musl~ with static musl specific ~RUSTFLAGS~. On macOS, reinstantiates ~pkgs~ with ~crossSystem =
    pkgs.stdenv.hostPlatform~ to force system library linking outside of the normal /nix/store. The resulting binary is only actually portable across macOS systems if the specific variants ~buildInputs~ avoid libraries directly from /nix/store libs, aka nixpkgs ~libiconv~ for most cli binaries. This is a you problem to make sure the binary is portable or to patchelf anything out after build., which is on you to arrange. Nop when combined with ~target~ ex: Windows which is effecively static already. Implies ~doCheck = false~.
  - ~wasm.enable~, ~wasm.bindgenCli~, ~wasm.wasmOptEnable~,
    ~wasm.wasmOptArgs~
    When enabled, pipes the wasm32 binary through ~wasm-bindgen~ and optionally ~wasm-opt~ into a ~wasm/~ output dir.
    ~wasm.bindgenCli~ is simply a function taking ~{ pkgs, lib }~ returning a package derivation, and has no default and *must* be supplied by the caller as its version needs to track whatever the crate's own  ~wasm-bindgen~ dependency needs, so this module deliberately doesn't provide one at all. This is also a you problem but if you're building for webassembly you're probs ok with that.
  - ~meta~
    Simply merged on top of ~defaultMeta~ if provided to set any meta attrsets.

As a silly example, a binary needing the mold linker on linux and a crate that needs to link against OpenSSL say for something that uses the aws-lc-sys crate (where this fragment comes from actually):

#+begin_src nix
{
  binaries.server = {
    nativeBuildInputs = { pkgs, lib, ... }:
      [ pkgs.openssl ]
      ++ lib.optionals pkgs.stdenv.isLinux [ pkgs.mold pkgs.pkg-config ];

    env = { pkgs, lib, buildInputs, ... }: {
      OPENSSL_DIR = "${pkgs.openssl.dev}";
      OPENSSL_LIB_DIR = "${pkgs.openssl.out}/lib";
      OPENSSL_INCLUDE_DIR = "${pkgs.openssl.dev}/include/";
      LD_LIBRARY_PATH = "$LD_LIBRARY_PATH:${lib.makeLibraryPath buildInputs}";
      RUSTFLAGS = "" + lib.optionalString pkgs.stdenv.isLinux "-C link-arg=-fuse-ld=mold ";
    };
  };
}
#+end_src

** Flake Example

You can call this flake directly if you have a simple use case where the defaults make sense:

#+begin_src nix
{
  outputs = { flakelight-rust, ... }: flakelight-rust ./. { };
  inputs.flakelight-rust.url = "github:mitchty/flakelight-rust";
}
#+end_src

Alternatively, add this flakelight module to an existing flakelight flake:

#+begin_src nix
{
  outputs = { flakelight, flakelight-rust, ... }: flakelight ./. {
    imports = [ flakelight-rust.flakelightModules.default ];
  };
  inputs = {
    flakelight.url = "github:nix-community/flakelight";
    flakelight-rust.url = "github:mitchty/flakelight-rust";
  };
}
#+end_src

Note you can always test updates to this flake against a local clone/checkout (this is here more for me cause I am a dumdum and forget often that I can do this):

#+begin_src sh
nix build --override-input flakelight-rust path:/absolute/path/to/flakelight-rust --no-write-lock-file
#+end_src

** Example projects

Just look at em if you got questions, they're intended to be more complete examples that a human could figure it out if they're nix language capable. These are also what CI tests against so that if something breaks I can know in advance.

~examples/minimal~

Probably what most might want to use, assumes a simple rust workspace setup. Tests out the portable derivations as well so failures happen sooner.

~examples/lib~

Not really any different to ~examples/minimal~ but for a library-only crate example. Shows that ~packages.default~ and the whole ~checks~ set with clippy, doc, nextest, deny et al work for a plain lib crate.

~examples/multi-binary~

Demonstrates using ~binaries~ options with a Cargo workspace containing a shared library crate and two binaries as a more complex example.

~examples/complect~

Demonstrates most of the insanity this whole thing got built for  ~binaries.NAME.variants~ builds two binaries with different ~pathDeps~ for the shared crates, a Windows cross compile target, a wasm32 target with a caller-pinned ~wasm-bindgen-cli~, a CUDA variant using custom ~pkgs~, a static musl linux binary, a portable macos variant, and
plain ~release~/~release-fast~ cargo-profile variants. Complecting most of what the module supports into one chungus cat example. This is built off of the insanity most of my crates seem to turn into lately somehow.

*** CI/Testing

This is a bit of a WIP but scripts/test-examples.sh is there to act as an integration test gate for this whole kit-n-kaboodle.

Current strategy is each example has no flake.nix so that every time the ci is ran the latest inputs are tested nix wise.

Cargo is different in that way CI can test automating updating cargo dep updates. The lock files are generally ignored. The idea is to test nix updates against known working cargo deps, then updating/testing cargo updates with the same.

#+begin_src sh
scripts/test-examples.sh                      # test every example against latest then revert
scripts/test-examples.sh multi-binary         # just test one example
scripts/test-examples.sh --update-cargo-lock  # test everything, keep passing Cargo.lock updates in git
#+end_src
